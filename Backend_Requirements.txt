1. RESPONSE ENVELOPE (ALL REST ENDPOINTS)
--------------------------------------------------------------------------------
All APIs should return the existing DynamicApiResponse shape:

  {
    "StatusCode": 0,          // 0 = success
    "Status": "Ok",
    "TotalRecords": number | null,
    "Message": string | null,
    "Model": T | null,
    "Value": unknown | null
  }

Auth: Bearer JWT in Authorization header unless noted otherwise.

5. PAGINATION RECOMMENDATIONS
--------------------------------------------------------------------------------
Yes — pagination is required for production chat. Recommended strategy:

5.1 Conversation list (sidebar)
  Type   : Offset OR cursor by lastActivityAt
  Recommend: Cursor-based infinite scroll
  Params : ?cursor=<iso timestamp or conversationId>&pageSize=30
  Why    : Users scroll down to load older chats; cursor avoids duplicates
           when new messages arrive during pagination.

5.2 Messages inside a conversation
  Type   : Cursor-based (REQUIRED for chat UX)
  Params : ?conversationId=&beforeMessageId=&pageSize=50
           OR ?before=<sentAt ISO>&pageSize=50
  Load   : Initial load = latest 50; scroll-up loads older pages
  Why    : Standard pattern (WhatsApp/Slack); offset pagination breaks
           when new messages append during fetch.

5.3 User picker (New Chat)
  Type   : Offset + search
  Params : ?search=&page=1&pageSize=20
  Why    : Admin-scale user lists; search debounced on frontend.

5.4 Message search
  Type   : Offset
  Params : ?conversationId=&query=&page=&pageSize=20
  Why    : Search results are static snapshots; offset is acceptable.

5.5 Notifications list
  Type   : Offset
  Params : ?page=&pageSize=20


6. ENCRYPTION (FUTURE — NOT IN CURRENT SCOPE)
--------------------------------------------------------------------------------
When the application is feature-complete, plan for:
  - TLS in transit (already via HTTPS/WSS)
  - Optional E2E encryption for message content (client-side keys)
  - Encrypted attachment storage
  - Key rotation and device management APIs

No encryption APIs are required from backend until that phase begins.


7. FRONTEND UI ACTIONS MAP (icons → backend)
--------------------------------------------------------------------------------
Header toolbar:
  Search        → GET /Messages/Search
  Voice call    → SignalR StartCall (audio) + call events
  Video call    → SignalR StartCall (video) + WebRTC signaling
  Info          → GET /Conversations/GetConversationDetails
  Members       → GET /Conversations/GetMembers (groups only)
  Mute          → POST /Conversations/Mute
  Pin           → POST /Conversations/Pin
  More          → Archive / Leave / Clear history endpoints

Composer toolbar:
  Attach        → POST /Messages/UploadAttachment
  Emoji         → Client-side (optional GET /Emojis)
  Voice note    → POST /Messages/UploadVoiceNote

Sidebar toolbar:
  Search chats  → GET /Conversations/Search
  Settings      → GET/PUT /Users/Profile


8. NOTES FOR BACKEND TEAM
--------------------------------------------------------------------------------
- Align SignalR event name: use MessageReceived OR ReceiveMessage consistently.
- SendMessage should return/echo messageId for optimistic UI reconciliation.
- Include sentAt (ISO 8601) on all message payloads.
- CORS: allow frontend origin OR rely on Next.js rewrite proxy (current setup).
- Rate-limit SendMessage and UploadAttachment to prevent abuse.
